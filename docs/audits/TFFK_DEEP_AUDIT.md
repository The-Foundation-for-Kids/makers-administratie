# TFFK deep technical, functional and architecture audit

Audit date: 2026-10-16  
Repository: `makers-administratie`, checked out `main` at `c488871`; comparison is limited to locally available `origin/*` refs.  
Scope: static review of tracked application source, manifests, migrations, tests and deployment workflow. No app boot, DB connection, external system access or dynamic security test was performed.

## Executive assessment

The project is a working-looking, conventional Laravel/Filament administration codebase, but the repository alone cannot establish production behavior. It concentrates business behavior in Filament resource schemas/actions and Eloquent model hooks, with little automated verification and little onboarding documentation. That makes changes hard to reason about and creates risk at authorization and data mutation boundaries.

Verified findings include a universally true `User::isAdmin()` helper, although its only visible caller currently returns no active privileged action; authorization assembled from overlapping roles, policies and resource query scopes; weak invitation-code generation; incomplete spreadsheet validation; possible stored HTML injection where user-editable fields are wrapped in `HtmlString`; non-transactional request-code generation; and deployment automation that migrates the target after a file sync without a visible test gate. The schema has limited referential constraints and some irreversible/data-moving migrations. The Composer PHP constraint also understates the locked dependencies' PHP floor.

No Laravel-to-WordPress API, webhook, client, shared-database declaration or data sync was found. WordPress integration and data ownership are unknown until the separate installation is inspected. A simple WordPress link to the Filament login needs no Laravel change; for the panel configured at root, the expected login path is `/login` on the backend host. The host comes from deployment/`APP_URL` and the generated route was not booted or verified in this audit. This is a link, not shared authentication or SSO.

## Phase 1: initial-audit gap analysis

The first audit correctly identified the framework family, basic modules, absence of repository-visible WordPress communication, weak invitation token generation, sparse tests, and automatic migrations during deployment. The following details needed correction or deeper work:

## Architecture and request path

`public/index.php` was not part of the earlier file inventory but is a standard entry point; Laravel bootstrap uses `bootstrap/app.php`, binding the HTTP kernel, console kernel and exception handler. `App\Http\Kernel` applies proxy/CORS/size/string middleware globally and defines web/API groups. `RouteServiceProvider` loads `routes/web.php` and `routes/api.php`. Filament adds panel routes from `AdminPanelProvider` and routes its pages and resources through Livewire. See [TFFK_ARCHITECTURE.md](TFFK_ARCHITECTURE.md).

Business mutations chiefly live in Filament form callbacks, bulk actions, import action handlers and `Clothing` model lifecycle hooks. No application service/repository/observer/job layer was found. The main write path is therefore a browser request handled through Filament/Livewire form state, Filament authorization, Eloquent model creation/update callbacks, the `clothing` table and activity-log package; Filament then returns the Livewire response/UI notification. This map is based on source wiring and not a runtime trace.

## Findings by severity

### High

1. **Unconditional admin helper — Medium, verified.** `app/Models/User.php:74-82` returns `true` before its intended name condition. `app/Filament/Resources/Clothing/Pages/EditClothing.php:24-33` is the only call site found; its returned action list contains only a commented-out deletion action, so no active privilege escalation is established from this helper alone. Replace it with explicit permission logic if still needed and test effective actions.
2. **Authorization is not one coherent server-side contract — High, verified structure; exploitability needs role/runtime verification.** `app/Providers/AuthServiceProvider.php:29-39` has unconditional `Gate::before` allow for `Super Admin` and a `Gate::after` callback returning false for non-super-admin. Resource policies use generated permission names; other code uses `super_admin`, `maakster`, `Maakster`, hard-coded names and active flag. `ClothingResource`, `OfferResource`, `CreatorResource`, `CollectorResource` and `CreatorHistoryResource` filter rows differently. A query filter protects list lookup only if all record routes/actions use it; no authorization tests demonstrate that. Cross-role record access and create/edit paths need systematic verification.
3. **Possible stored XSS — High, likely conditional.** `Clothing::adres()` returns an `HtmlString` after concatenating agency fields (`app/Models/Clothing.php:151-160`). `ClothingResource`, `CompletedResource`, `OfferResource`, `CreatorResource`, `CreatorHistoryResource` and agency relation UI also build `HtmlString` from model values (examples `ClothingResource.php:98-108, 195-210`; `OfferResource.php:80-105`). If users with write/import rights can insert markup into those fields, another panel user may execute it when viewing a record. Do not treat as remotely exploitable without confirming write roles and escaping behavior. Use escaped text or narrowly sanitized markup; verify safely with harmless markup in isolated local fixtures.
4. **Invitation token has inadequate entropy and lifecycle controls — High, verified.** `ManageUserInvitations.php:25-27` derives a 32-character MD5 value from a single-digit random number, email and current time. `user_invitations.code` is nullable, length 32 and not unique (`database/migrations/2026_01_08_create_user_invitation table.php:11-17`). Registration has rate limiting and deletes a used invitation (`Register.php:28-72`), but no expiration or explicit uniqueness/atomic consume is visible. A guessed/colliding token could register an account for the invitation email and receive the invitation role. Strengthen generation/storage, expiry and atomic single use, then test races and rejected cases.
5. **Spreadsheet import accepts insufficiently validated rows — High, verified.** `ClothingsImport::rules()` is empty and `uniqueBy()` returns `email` (`app/Imports/ClothingsImport.php:69-82`), though its row mapping creates clothing request data. `ClothingImportAction` loops failures but still sends success (`.../ClothingImportAction.php:85-100`). Invalid rows, duplicates and FK errors may lead to partial imports or misleading operator feedback.
6. **Deployment runs schema changes without visible quality gates — High, verified config.** `.github/workflows/main.yml:3-7,30-39,52-83` pushes to `prod`, `test`, `sendy`; installs dependencies, packages source, syncs with `rsync --delete`, then runs `artisan migrate`, Shield seeding and config/route cache commands. No tests, build, health check or documented rollback are present in this workflow. Actual branch protection, backup and recovery are unknown.
7. **Seeder contains a weak, hard-coded account credential — High, verified but conditional.** `database/seeders/UserSeeder.php:16-28` inserts a user with a trivially weak literal password and fixed role pivot ID. `DatabaseSeeder` invokes it (`database/seeders/DatabaseSeeder.php:21-27`), though the deployment workflow invokes only `ShieldSeeder`, not `DatabaseSeeder`. The seeded account may be usable only if a maintainer runs the full seeder in an environment. Do not run it; remove/replace the credential and make seeders safe for their intended environment. No credential value is reproduced here.

### Medium

8. **Request code generation can race and is not constrained unique — Medium/High, verified structure.** `Clothing::boot()` queries latest matching code and increments it (`app/Models/Clothing.php:194-214`), without a transaction/lock. The initial clothing migration has nullable `Code` and no unique index (`database/migrations/2023_02_24_220429_create_clothing_table.php:16-20`). Concurrent creates for one agency/year can issue duplicate identifiers. Database engine collation and existing data are unknown.
9. **Eloquent agency owner relation likely uses the wrong key — Medium, verified relationship declaration.** `Agency` fillable field and `User::agency()` use `verzamel_user_id` (`Agency.php:13-33`, `User.php:38-41`), but `Agency::verzamel_user()` calls `belongsTo(User::class)` without key override (`Agency.php:41-45`), so convention derives `user_id`. A call through that relation may return incorrect/null owner; no active use was found in inspected paths. Verify usages and deployed schema.
10. **Foreign-key coverage is incomplete and actor attribution is denormalized — Medium, verified.** Only `clothing.agency_id` is constrained in the initial table; `maakster_id` and several `Gebruiker_*` IDs are nullable integers (`create_clothing_table.php:20,28,44-60`). Orphaned/deleted users can leave stale IDs; migration must be data-aware.
11. **Business state rules are loose and duplicated — Medium/High, verified.** `Clothing::setStatus()` allows any valid status from any prior status and returns `true` for an invalid new value (`Clothing.php:103-150`). Several resources duplicate status lists and directly write status in `afterStateUpdated` handlers. Assignment/deadline side effects can be bypassed by direct form field edits. The agreed transition matrix is unknown.
12. **Hard-coded operational year choices and role filters can age out — Medium, verified.** `resources/views/livewire/select-year.blade.php:3-9` lists 2023–2026. Other options are generated from data. Selected year is mutable through an authenticated Livewire component (`app/Livewire/SelectYear.php:12-24`); validation/coercion of arbitrary selected values is not shown.
13. **MySQL-specific SQL in reporting/sorting — Medium, verified.** `Agency::month*()` and `AgencyReport` use `month()`; clothing tables use `ISNULL()` ordering (`app/Models/Agency.php:59-104`; `app/Filament/Pages/AgencyReport.php`; `ClothingResource.php:247`). `database/migrations/2025_12_10_clothing_move_2023.php` uses MySQL `insertUsing`; other migrations use `REGEXP_INSTR` and `substr`. Deployment is cPanel/MySQL-looking but DB engine is unknown; SQLite tests may fail without query adaptation.
14. **Large table report computes many counts — Medium, likely performance risk.** `AgencyReport` defines total and twelve month-count columns using relation count queries over archived clothing (`app/Filament/Pages/AgencyReport.php:65-120+`); no appropriate indexes are apparent in the checked migrations for year/status/datum columns. Query plan and row counts are unknown; inspect with anonymized staging-sized data.
15. **A login middleware performs a user write on each authenticated panel request — Medium, verified.** `LogSuccessfulLogin::handle()` updates `last_login_at` for every authenticated request rather than only login events (`app/Http/Middleware/LogSuccessfulLogin.php:18-24`); panel middleware includes it (`AdminPanelProvider.php`). This can distort last-login semantics and adds writes to every panel request.
16. **Password recovery and verification behavior needs reconciliation — Medium, verified configuration/code, runtime uncertain.** Filament panel enables password reset (`AdminPanelProvider.php:36`); `config/auth.php:81-90` points reset broker to `password_reset_tokens`, while migration `2014_10_12_100000_create_password_resets_table.php` creates `password_resets`. Laravel 12 commonly has a different default migration; no matching `password_reset_tokens` migration was found. Custom registration emits `Registered` but `User` does not implement `MustVerifyEmail`; `app()->bind(SendEmailVerificationNotification::class)` in `Register.php:62-65` is unusual. Verify reset/verification in isolated setup.
17. **Upload/import path and error behavior need hardening — Medium, needs runtime verification.** `ClothingImportAction` uses `FileUpload`, `preserveFilenames()` and `storeFiles(false)` and accepts a list of MIME/extension strings (`.../ClothingImportAction.php:53-59`). File storage is marked private, reducing public exposure, but allowed type enforcement, size limits, parser failures, cleanup and success messaging need verification against the installed Filament/Excel package versions.
18. **Migration rollback and data movement are weakly reversible — Medium, verified.** Year-archive migrations move rows between tables with `insertUsing` and don't show complete reverse copy; archive migration and selected-year migration have empty `down()` methods. `2026_01_10_clothing_dropobsolete.php` drops columns with a down path that may not restore values. Data impact must be rehearsed on a non-production snapshot.
19. **Data retention and privacy boundaries are undocumented — Medium/Needs verification.** Clothing fields include recipient characteristics, wishes, contact details, delivery addresses, tracking codes, notes and activity history; activity logging logs fillable changed fields (`Clothing.php:25-68,173-176`). Authentication logging is configured. Retention, access/export permissions and personal-data deletion expectations are unknown.
20. **CORS is wildcard for API paths — Low/Medium conditional.** `config/cors.php:18-34` allows all origins/methods/headers on `api/*` and Sanctum CSRF cookie path, credentials false. This is not alone an authentication bypass; with the current token-authenticated API surface risk is limited. Reassess origins before adding browser-cookie API or sensitive endpoints.
21. **Tracked migrations do not describe a complete clean-install schema — High, verified absence; deployed provisioning unknown.** No migration creating `agencies`, `agency_planning`, or Spatie roles/permissions pivot tables appears in `database/migrations/`, while `2023_02_24_220429_create_clothing_table.php:20` declares `agency_id` constrained to `agencies`, resources reference roles, and `ShieldSeeder` uses permission tables. A clean install may fail or require an undocumented pre-provisioned schema. Verify using a disposable database only and document the authoritative schema bootstrap.

## Dependency and upgrade assessment

Verified manifests: `composer.json` requires PHP `^8.1`, Laravel 12, Filament `~4.0`; lock pins Laravel `v12.0.0`, Filament `v4.7.1`, Sanctum `v4.3.1`, Maatwebsite Excel `3.1.67`, PHPUnit 10 constraint. Several locked Filament/Laravel packages declare PHP `^8.2`, so PHP 8.1 is not a viable installation target for this lock despite the root constraint. Deployment CI uses PHP 8.4. This is a manifest mismatch, not proof of production runtime failure.

As of the audit date, Laravel's official support table lists Laravel 12 security fixes through 2027-02-24, with bug-fix support ending 2026-08-13; the lock's `12.0.0` is the initial patch release and should be brought current after test coverage is established. Filament's v4 upgrade guide lists PHP 8.2+ and Laravel 11.28+; current Filament documentation labels v4 previous, so plan a supported-major review rather than assuming Filament 4 is current. PHP 8.1 is end-of-life; PHP 8.4 remains security supported through 2028-12-31. See [Laravel 12 support table](https://laravel.com/framework/docs/12.x/releases), [Filament 4 requirements](https://filamentphp.com/docs/4.x/upgrade-guide/), [PHP supported versions](https://www.php.net/supported-versions.php), [PHP unsupported versions](https://www.php.net/eol.php).

No Composer advisory audit was run. Package vulnerability status must be checked with Composer audit against the actual deployed lock and runtime before modernization decisions. Upgrade blockers include missing meaningful tests, Filament resource custom APIs, PHP requirement mismatch, MySQL-specific query behavior, and no isolated local DB documented.

## Canonical Filament login link

`AdminPanelProvider` sets panel path to `''` and enables `->login()` (`app/Providers/Filament/AdminPanelProvider.php:30-38`). Thus the expected browser login URL is `https://<backend-host>/login` (root panel); configured host must be confirmed from the backend deployment's `APP_URL`/cPanel domain. The exact generated route was not runtime-inspected. WordPress may link to this URL with a normal anchor/button and needs no Laravel code change for a simple redirect. Users still authenticate separately in Laravel. Shared session, WordPress credentials, SSO and account provisioning are not evidenced; any such request is a distinct integration project.

No app boot, DB access, migration, seeder, Composer install, remote fetch, WordPress/cPanel login or vulnerability probe was performed.
